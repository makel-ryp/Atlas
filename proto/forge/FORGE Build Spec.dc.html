FORGE Build Specification

Every constant, rule, and state transition needed to rebuild FORGE against a real backend. The HTML prototype is the visual reference; this document is the contract. Where the two disagree, this document wins.

READ THIS FIRST

Four rules that are load-bearing and easy to violate by accident:

  1. The composite index is derived, never stored. Persist facet indices only; recompute the composite on read. Two copies will drift.
  2. An incomplete drill never becomes a headline number. Completeness is defined per drill (§3.4) — 20 shots for the shot-count drills, 18 holes played for Putt 18. Never hard-code 20. Incomplete results are stored, flagged provisional, and excluded from the current picture.
  3. Lower is better, everywhere. Indices are handicap-scaled. Negative values print with a leading + (golf convention) — -2.4 displays as +2.4.
  4. Every assignment carries a source. coach beats player beats auto. This one field drives inert stations, coach visibility, and what the app may reshuffle.

2 · Scoring engine

This section is exhaustive by design. A wrong slope produces plausible-but-wrong indices, which is the worst available failure mode — it is not visible in QA and it silently misdirects a player's practice for months. Copy the numbers; do not re-derive them.

2.1 Facet weights

Used for the composite. Weights of scored facets are renormalised — a session that skipped putting is not penalised for it.

2.2 Scored drills — approach, ATG, makeables

All three share one formula. Each shot yields a value from its level's option set; the values are summed, scaled to a full 20 shots, and mapped onto the handicap scale by the facet's base and slope.

total = Σ shot_values × (20 / shots_logged)
index = clamp(base[level] + total × slope, −6, 40) rounded to 1 dp
// fewer than 5 shots logged ⇒ index is null, not 0
FACETBASE · L1–L4SLOPESHOTS
Approach[20, 12, 5, 0]0.620
ATG (chipping)[20, 12, 5, 0]0.620
Makeables (putting predictor)[8, 4, 1, −1]0.920
Putting is different — the Putting Index is Putt 18, not Makeables. The formula above produces the Makeables score, which is a predictor, not the Index. See §7 for the outcome/predictor split and how the Putting Index is computed.

2.3 Driving

Driving does not use base/slope. It anchors on a distance-derived baseline handicap and adjusts by fairways hit against bad misses, where a bad miss costs double a fairway.

fairways = count(value == 2)  // centre column
bad     = count(value == 0)  // see the asymmetry note below
scale   = 20 / shots_logged
adj     = (fairways − bad × 2) × scale
index   = clamp(baseline_hcp + (8 − adj), −6, 40)
Asymmetry — prototype bug, decide before building. The formula above reproduces the prototype exactly: only column 0 (bad left) counts as a bad miss. Column 4 (bad right) is scored as neutral, so a right-side blow-up costs nothing. The 0 or 4 form does appear in the driving summary tiles, which is why the displayed "bad misses" count disagrees with the index. This is almost certainly unintended: the intended behaviour is symmetric — bad = count(value == 0 or value == 4). Build it symmetric, and treat any prototype driving index as non-comparable.

Columns are 0–4 left to right: 0 big miss left, 1 small miss left, 2 fairway, 3 small miss right, 4 big miss right. Small misses are neutral by design — they neither help nor hurt.

DRIVING HAS ONE FIXED CORRIDOR — NO LEVELS, NO LADDER

The corridor is the same for every player at every standard, so driving indices are directly comparable and driving is exempt from §4 entirely. Its level is always 0 and no promotion or demotion applies.

2.5 Modes

Drivingstock · variable — stock is twenty of the player's own shot with no calls; variable calls two draws and two fades at random across the 20. Same scoring either way.
Approachstock · variable — variable adds a D/F/W shape call to each shot.
ATGfairway · rough · bunker — same option set, different lie. Levels track independently per lie.
Puttingcourse Putt 18 — this IS the Putting Index · makeables (formerly rotation), lag, and stroke are predictors: each carries its own score and none of them enters the Index directly. See §7.
Putt 18 and expected putts. Eighteen holes are generated from the session seed across five distance bands — 3–6, 6–12, 12–20, 20–30, 30–50 ft — with selection weights [5, 5, 4, 3, 3]. Par for the round is the sum of expected_putts(d) = 0.60 + 0.46 × ln(max(d, 2)). Strokes gained per hole is expected minus actual.

2.6 Handicap scale and display

  • Range. Target runs from the gender floor to 30. The floor is the first entry of the gender's named-level table: men −5 (PGA Tour), women −4 (LPGA Tour). It is a continuous scale, not discrete steps. Note the floor comes from the named-level table, not from the carry tables in §2.3 — those map carry to a driving baseline only.
  • Named levels. Exact handicap values get a label instead of a number. Men: −5 PGA Tour · −4 Korn Ferry · −3 Division I · −2 Division II · −1 Division III · 0 Scratch. Women: −4 LPGA Tour · −3 Epson Tour · −2 Division I · 0 Scratch · 2 Division II · 3 Division III. Any other value renders as "n Handicap".
  • Clamp. Every index is clamped to −6…40 and rounded to one decimal, on write and on read.
  • Position on the bar. pos% = clamp((x + 6) / 36 × 100, 0, 100).
  • Zones. ELITE floor…0 · LOW 0…5 · MID 5…15 · HIGH 15…30. Upper bound exclusive except the last.
  • Sign. Negative prints as +: −2.4 → "+2.4". Values within 0.05 of zero print as 0.0, never +0.0.
  • Colour, against target T. index ≤ T + 0.4 green · index ≥ T + 3 crimson · otherwise silver. Crimson is reserved for numbers and the primary-leak label; it is never decorative.

2.7 The current picture

"Current" is not "most recent session." Sessions score arbitrary subsets, so each facet independently carries forward its last complete value:

for each facet:
  walk sessions newest → oldest
  take the first with a non-null index AND is_complete  // §3.4
  record its value and its age (index in the walk)
composite = weighted mean of those values
// trend: recompute the same way over sessions older than the
// newest contributing session. Both sides must resolve
// identically, or the delta compares a session to itself.

Missing facets are never treated as zero. A player who has not putted in a month still shows their last complete putting index, and the composite is renormalised over what exists.

3 · Session state machine

A session is a container the player moves through station by station. In the prototype this logic is spread across the render function and is only fully knowable by reading it; here it is explicit.

3.1 Lifecycle

created → in_progress → complete, or abandoned. Created allocates the seed. Complete is reached by explicit finish, never by scoring the last shot — players routinely re-score. Abandoned is set by the stale-session prompt (§3.5), never automatically.

3.2 Stations

Four stations in fixed order: driving, approach, ATG, putting. The player may jump to any of them at any time; order is presentation, not a constraint. Each station is independently untouched, partial, or scored. A station may be skipped entirely.

3.3 Entry methods

Head-scoring is the default for approach, ATG, and putting: the player hits all twenty, then tallies outcomes. Shot-by-shot is opt-in. Driving defaults to the abacus.

tallyCounts per outcome. Must sum to 20 to be complete; over 20 is an error state, under 20 is provisional.
shot_by_shotOne tap per ball, ordered. The only method that yields real per-shot analytics.
abacusDriving: tap one of five columns per ball.
column_totalsDriving: enter how many balls finished in each of the five piles. Preferred over tapping — five numbers instead of twenty taps, and it writes the same 20 synthetic column rows. Sum must equal 20 to be complete.
photoCut. Photographing the tray needs vision work to beat typing five numbers, and does not. Removed from the prototype; do not build.
monitorImport a launch-monitor screenshot. Stubbed — the filename is ignored and values are fabricated. See §6.4.

3.4 Completeness and provisional scores

CANONICAL COMPLETENESS RULE — REFERENCED EVERYWHERE ELSE

Completeness is defined per drill, computed once on write into session_facets.is_complete, and read from that flag by every consumer. No consumer re-derives a threshold, and nothing hard-codes 20.

Driving · Approach · ATG · Makeablesshot_count >= 20
Putt 18holes_played == 18 — never a putt count. A round produces roughly 28–40 putts, so a Putt 18 abandoned after six holes can already exceed 20 logged putts; testing shot_count there would publish a bogus Putting Index and satisfy an assignment.
Lagshot_count >= 20
Stroke Testshot_count >= 20

An incomplete result is stored and is visible in the session detail, but is excluded from the current picture, the composite, the trend, the ladder, and assignment completion. It appears as provisional and never as a headline number. Legacy records with no counts are treated as complete unless explicitly flagged.

3.5 Resume

Every shot is written through immediately — a dead battery must lose nothing. Three affordances, none of which exist yet:

  1. Resume card on Today when an incomplete session exists, showing which stations are done.
  2. Inert skipped stations — visibly present, tappable, marked as not counted.
  3. Stale-session prompt when an incomplete session is older than 12 hours: resume, or close it out with what was scored.

3.6 Mode switching and the weekly check-in

Switching mode mid-station discards that station's shots and starts it clean — the two modes are different tests and their shots cannot be pooled. The UI must say so before it happens. Separately, when usga_updated_at is more than 7 days old, Today shows the handicap check-in; confirming re-bases the target, snoozing writes now − 5 days so it returns in 2.

4 · Challenge ladder

  • Clear — a session's facet index at or below the target. One clear promotes.
  • Miss — above it. Three consecutive misses demote.
  • Counters are per facet, and reset on any level change. Provisional facets count as neither.
  • Levels are bounded L1–L4: no promotion above L4, no demotion below L1.
  • Promotion and demotion are offered, not automatic — the player confirms. This is deliberate; a silent level change invalidates the comparison they were making.
  • A level change never rewrites history. Past session_facets keep the level they were played at.
  • The ladder is the only thing that sets level. No coach action, assignment, or admin path may change a player's rung. See §5.5.
  • Driving is exempt. It has one fixed corridor (§2.3), so it has no level, no rung, and no promotion or demotion. The ladder screen shows it as FIXED.

5 · Assignments, schedule, and ownership

5.1 Precedence

coach > player > auto. A coach assignment cannot be dismissed by the player, only completed or expired. A player's pinned focus fills whatever the coach has not claimed. auto is what the app proposes from the current leak, and is replaced freely by either of the others.

5.2 Inertness

When any assignment is outstanding, the other drills stay tappable but marked inert — they score and store normally, and they do not satisfy the assignment. This is the anti-scope-creep rule: a player who wanders is never blocked, but is never confused about whether the prescribed work is done.

5.3 Cadence and expiry

dayAppears every block. Never auto-expires; the coach pulls it.
weekSatisfied by one qualifying session; expires end of the ISO week.
onceExpires on completion.

Qualifying session = matching facet, matching mode if the assignment specifies one, played at the player's current ladder level, and complete per §3.4. A provisional score never completes an assignment. Completion is computed from the arriving session, never from a player tapping "done."

5.5 Level is owned by the ladder, not the coach

A coach assigns the drill, never the level. The coach picks facet, mode, cadence, and note. The level the player runs it at is whatever their ladder has them on for that facet — earned by clearing (§4), lost after three straight misses. The coach console shows each selected player's current level as read-only context so the coach knows what standard they are asking for, and it may differ per player in the same multi-player assignment.

Consequences to build for: an assignment created today may be satisfied at a different level tomorrow if the player promotes in between — that is correct and must not invalidate the assignment. A coach who wants a player working at an easier standard does not lower the assignment; the ladder does that on its own after three misses. No API accepts a coach-supplied level.

5.4 Player schedule

A session is always 30 minutes — that is the product's fixed unit and is not configurable. The player sets blocks per week (1–7), which drives the streak, the nag, and the coach's "behind" flag. They may also pin one facet as a focus for up to two weeks, after which it expires back to auto. The player owns cadence; a coach adds work on top of it but never overrides how often the player has committed to train.

6.2 Auth and RLS

Supabase auth. A player reads and writes only rows where player_id = auth.uid(). A coach reads rows for players joined through an accepted coach_players row, and writes only assignments and coach_notes — never a player's sessions or shots. Coaches use a separate web app; the two clients share the API and nothing else.

6.3 Connectivity — deferred submit, not a sync queue

Do not build an offline sync queue. A scored session is roughly 20 integers per drill — under 2 KB. That transmits on one bar of signal. Offline-first architecture (queued mutations, replay ordering, per-field conflict resolution) is a multi-week build that buys nothing here, and the real failure mode is flaky signal rather than no signal — which a retry handles as well as a queue does.

The required behaviour, in full:

  1. Local write-through on every tap. The live session is written to local storage as it is scored. This — not the network layer — is what protects a player against a dead battery or a closed tab.
  2. One submit at completion, carrying a client-generated idempotency key so a repeated send can never duplicate a session.
  3. On failure, keep it local and marked unsent. Retry quietly on next app open and on network return. The player is never blocked from continuing.
  4. One unobtrusive "not saved yet" indicator. No modal, no spinner, no retry button.

No queue, no replay ordering, no conflict resolution: a single player scoring a single session on a single device cannot conflict with itself. Revisit only if two devices, or a coach scoring alongside a player, ever write to the same session. Independently of all of the above, the client keeps a schema version and migrates on read — the prototype's unversioned localStorage key silently wipes returning users on any shape change.

6.4 Known stubs to replace

  • Photo tally — cut, not deferred. Replaced by direct per-column total entry, which is faster and needs no parsing.

7 · Outcomes, predictors, and learning readiness

This section is what lets the product eventually answer does this drill actually improve your scoring? — without building any machine learning in v1. It requires a structural distinction the prototype does not currently make.

7.1 The distinction

OutcomeA drill that measures performance worth caring about for its own sake, under conditions resembling play. It is the facet's Index. One per facet.
PredictorA drill that measures a mechanism believed to move the outcome. Carries its own score. Never enters the Index. Its claim to matter is testable, and the point of the data model is to test it.

Putting is the first facet built this way. The same pattern is intended for the other three over time — each gains one outcome drill and a set of predictors — but do not restructure driving, approach, or ATG in v1. They keep their current single-index behaviour until there is a designed outcome drill for each.

7.2 Putting, restructured

Putting Index = Putt 18. Eighteen generated holes, scored against expected putts (§2.5). This is the outcome: a simulated round, which is the thing a player is actually trying to improve. It replaces Makeables as the Index.

The three predictors, with their population weights — hand-set from coaching judgment, used from day one, requiring no data:

MAKEABLES
50%
Make rate at scoring distance. The 100° rotation drill, renamed.
LAG
30%
Distance control from long range. Three-putt avoidance.
STROKE TEST
20%
Start-line quality through the gate. The most mechanical, least predictive.

These weights drive assignment suggestion: the predictor with the worst standardised score, weighted, is what the app proposes working on. They are a prior, not a truth — §7.4 replaces them per player once there is evidence. Note these are a different weight system from the composite facet weights in §2.1 and must not be conflated: §2.1 weights combine facets into one index; §7.2 weights rank predictors within one facet.

Needs calibration before build. Putt 18 produces strokes gained against expected putts for a round; the Putting Index must be on the −6…40 handicap scale like every other facet. The mapping is index = putting_base − sg_total × k. Neither putting_base nor k is derivable from the prototype — they must be set against known reference rounds (a scratch player's Putt 18, a 20-handicap's) before any index is published. Do not ship a guessed constant.

7.3 What must be logged — the only expensive mistake

Learning later needs exactly three things, and all three are cheap now and unrecoverable in hindsight:

  1. Exposure — which drill was run, when, and how much. Every predictor must be a first-class session_facets row with its own timestamp. Lag and Stroke Test are currently stored as loose extras blobs; that ends.
  2. Outcome — Putt 18 scores, repeated over time, in their own outcomes rows: player_id, measured_on, kind (putt18 · later round_score · usga_handicap), value, session_id null.
  3. Time alignment — nothing more than honest timestamps on both, so the question "did work in the last N weeks move this week's number" is answerable by a query.
Store predictor results as numbers, never as display strings. Stroke test writes on_line_pct 0.87, not "13 of 20 on line". Lag writes avg_proximity_ft 3.4. Makeables writes make rate per distance band. The prototype renders these to text and discards the value — every one of them is a model feature and belongs in a typed column.

SETTLED SCOPE DECISIONS
Launch-monitor import — out of v1. Manual entry only.

Driving and approach shots are entered by hand: carry and offline for driving, pin distance and proximity for approach. No screenshot OCR, no vendor CSV parsers.

Why not OCR: every monitor app has its own layout that changes with app updates, so each device is a separately-maintained template that breaks silently. Monitor summary screens show averages, not per-shot rows — and the index depends on shot-level dispersion, so averages cannot produce an honest number. A misread digit corrupts a handicap, which forces a confirm-every-value review screen and erases most of the time saved.

Why not CSV yet: the parser work is small (2–3 days per small set of vendors) but each one needs a real sample export to test against, and approach still requires a hand-entered pin distance regardless — carry alone never yields proximity.

Consequence: the shot schema stays the single source of truth for all four facets. CSV import, if it is ever earned, writes into that same schema and touches no scoring code.

OPEN DECISIONS
