## 🔴 First sign-in asks for a date of birth, and that is deliberate

Both rows have `date_of_birth = NULL`, so the first thing each account shows is the DOB screen —
`POST /api/session` answers **403 `dob_required`** until it is set.

This is not an oversight. STATUS.md's rule: *"real people's birthdays are deliberately NOT
invented."* It feeds the 13+ floor and the guardian branch, so a fabricated value is a fabricated
safeguarding decision. The demo accounts (Avery, Sam) have one because they are fictional; Luke is
not.

**Verified 2026-10-19** by setting a placeholder, confirming both accounts render
(coach → `view: roster`, roster `['Luke Benoit (student)']`; student → `view: today`, no roster),
then **clearing it again**.

🔴 **CORRECTION 2026-10-21 — this said "the only thing standing between Luke and the app is
one screen", and that was WRONG.** It was verified through `/proto/dashboard`, which is served
directly and **bypasses the React shell's gates**. The real sign-in path is
`client/src/App.tsx:265-270`, which also gates a player on a COMPLETED PRACTICE DNA RUN. Neither of
Luke's accounts has one.

So his actual first run is: **sign in → date of birth → the whole Practice DNA intake → Today.**
Budget for the intake, and warn him the DOB is write-once (a typo needs SQL to undo) and the intake
answers are not editable afterwards either.

The lesson for anyone verifying this again: **fetching `/proto/dashboard` proves the data layer,
not the journey.** A gate that lives in the SPA is invisible to curl.

## Allowlist changes made

`ATLAS_SIGNUP_ALLOWLIST` is per-environment and gates **first-sign-in auto-grant only** — it does
not affect accounts that already hold a role.

- **Testing:** 14 → 15 entries, added `luke.benoit@gmail.com`.
- **production:** 14 → 13 entries, **removed `luke@rypgolf.com`** (Makel's decision, 2026-10-19).

🔴 **Why production mattered.** Testing and production share ONE Firebase project, `rypstick-ios`
— the same project behind the live RYP Stick iOS app and its ~28k real customer accounts. A
credential that works on Testing therefore works on production too, and production's allowlist
admitted `luke@rypgolf.com`, so a demo sign-in could have auto-provisioned him on the **live main
database**. He had no rows on `main` (checked), so nothing was lost by closing it. To undo, add the
address back to production's list.
